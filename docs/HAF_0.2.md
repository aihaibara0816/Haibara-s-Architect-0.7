# HAF 0.2：现有能力、工作流与交付

2026-10-23。当前可以输出带参数、材料清单、真实 NBT 回读预览和反馈记录的离线建筑审阅版。最终游戏效果仍需目标版本导入验收；新建筑仍要专门研究并编写或调整案例适配器。

## 这次发布是什么

统一命名为 HAF 0.2（Python 版本 0.2.0）；加入只读版本/控制目录入口，整理已经存在的灯光、细节与伪内饰能力。没有重新生成整栋，也没有把局部实验改名成完整新建筑。保留全部历史 run、案例参数和随机 namespace，HA0.3 和广州塔 V5 原始工程继续作为历史资产。

## 目前工作流

1. 确定建筑、年代、范围、尺度和原版本；查最新工程、真实输入与失败记录。
2. HA 研究不限图片数量，按主体/幕墙/屋顶/裙楼/场地/内部组织多向日夜证据；可选三维模型单独检查单位、坐标、实例、年代与质量。没有模型继续纯图片。
3. 按构件做取舍：来源和观察 → component_id → 参数/几何 → 消费代码 → 验收。选择合适证据，不把不同方案机械取平均。
4. 关键局部先验证薄构件、前后层、镂空、灯体尺度和家具净空。固定外部灯带与室内随机亮暗分别控制。
5. HAF 已注册适配器生成新 run；参数、来源和随机种子存档。新建筑先补适配器，不能直接改 --case 名字。
6. 最终 NBT 独立回读，检查方块状态、材料、尺寸、归属、局部差分和拼合；做同机位日夜全景、四向、近景和必要剖切。
7. 离线审阅交付 → 按构件反馈 → 针对缺口修订；最终目标游戏导入验证材质、碰撞、通行、灯光及导入行为。

原有授权内继续执行；不把上述步骤变成每一步都要用户确认。只有超出范围或整体替换 workflow 才另行确认。

## 夜景研究新增归纳

三层分开：固定外部照明（横带、竖向、塔冠、裙楼/场地）；室内与窗灯（功能分区、亮暗房间、可见灯具、家具）；高层航空障碍灯（位置、层级、颜色、尺度、遮挡、常亮/闪烁证据）。

每项记录来源、位置与标高依据、可见面、日期/模式、色彩类别、不确定性、材料候选、代码消费者及日夜验收。未知值不补造。实景固定图案先确定，房间随机只深化剩余部分。

红玻璃包荧石是灯体候选；不能据此声称游戏产生红色投射光或闪烁。在整栋同尺度下比较 3×3 包罩、1×1 嵌入罩和更小灯体。背面未知不自动镜像补成事实；有需要时再做独立法规研究，本规则不代表法规合规结论。

## 到最终产出还差什么

| 优先级 | 下一步 | 达标条件 |
|---|---|---|
| 当前建筑 P0 | 周大福屋顶斜面/方向、夜间固定灯带与障碍灯位置核实 | 多视角依据明确；工作坐标与地理方位区分；标高/背面仍未知处显式保留估算 |
| 当前建筑 P0 | 将用户选中的薄肋、灯体和伪内饰样板接入一个整栋新 run | 有参数消费者；结构/幕墙不被灯位破坏；家具净高/支撑/进深合格；同种子复现，改灯种子不改变固定灯带/主体 |
| 最终游戏 P1 | 指定 Java/基岩与版本、导入器和光影/资源包环境后实测 | 真正导入；方块不缺失；玻璃/墙/栏连接、碰撞、通行、灯具近远景及夜间冷暖效果可接受 |
| 可交付 P1 | 固定打包与反馈记录 | 建筑文件、材料、放置说明、参数/来源、预览、四层验收和源码均对应同一 run/hash；不能用旧 QA 验证新 NBT |
| 通用化 P2 | 再做低层或不同风格建筑迁移 | 不套用广州塔/CTF 构件数量与形式；四周围护、屋顶、裙楼、空洞和灯光均重新由证据决定 |

获取 SU 不是当前路线的硬前置条件。CTF 已查到公开模型线索，但尚无实际下载、解析的网格；不得将网页缩略图当成模型输入。其他格式可走已有模型研究入口，但需实际验证新文件。

## 交付应包含

主 NBT（或实际写出的 schem），必要分块与偏移；材料数量和 blockstate；版本/尺寸/原点/方位/高度/导入限制；参数、证据和构件取舍；同机位近远景、四向与夜景；文件/几何/视觉/游戏四层状态；可回顾反馈和源码。

示例案例已经分别有多项交付工具，但还没有替任意新建筑自动完成以上全部内容的通用发布器。离线报告不能替代游戏验收；伪内饰不能宣称完整可游玩的实楼室内。
