# 0.7 规则入口

场景、内饰、植物、工业经验已归入 [六领域规则](skills07.md) 与 `knowledge/workflow07.json`；执行能力见 [工作流](workflow.md)。个人安装未同步，不能以仓库规则发布代替个人 Skill 安装记录。以下为历史研究说明。


# 概念设计与技能规则：Haibara’s Architect 0.6 研究经验

本文整理 `gafacraft-concept-design` 的设计方法、可执行部分及尚未解决的问题，供 Haibara’s Architect 0.6 集成与后续案例复用。依据为截至 2026-11-01 的规则、案例记录、原始脚本审计及限定范围测试。它是公开流程文档，不是技能安装包，也不表示任意建筑、地形或内饰已经可以自动完成。

本次可独立分发的代码只有两个实验性立面计划器：`plan_openings.py` 和 `plan_variation.py`。它们生成 JSON 计划，必须由人先确认空间边界；不默认执行，不直接写出 Minecraft NBT。完整限制见 [概念设计已知问题](known-issues-concept.md)。

## 2. 先确定工作路线，再确定空间

原创设计、受证据约束的补全、现实建筑复原是三条不同路线。

- **原创设计**：由用途、场地、关键词与硬约束建立方案；不需要为证明“没有同名建筑”而进行无意义检索。
- **受约束补全**：建筑身份与部分几何已确定，未知部分明确标注建议；已认可部分保持不变。
- **现实复原**：资料足够时进入建筑研究与 Architect 流程；生成图不能作为测量证据。身份尚不清楚时，不把忠实复原悄悄改成原创。

用途与风格也要分开。“现代”“日式”“中式”并不自动意味着某种屋顶、旧化或乡村语汇。先确定建筑供谁使用、有哪些活动，再选择体量、空间、结构表达和材料。

相关技能的职责不能互相冒名：

| 入口 | 职责 | 与本流程的关系 |
|---|---|---|
| `gafacraft-concept-design` | 原创、受约束补全、功能内饰与场地设计规则 | 先形成可审查空间和构件计划 |
| `gafacraft-ha-research` | 面向自建引擎的高保真现实建筑证据研究 | 现实复原有足够资料时优先进入；图片数量按证据需要确定 |
| `gafacraft-architect` | 组织研究、几何建造、读回和对照交付 | 消费可执行数据，保留尚未接入的字段和验收缺口 |
| `gafacraft-building-reference` | 面向外部建筑AI的参考资料包 | 六图默认属于该外部资料包，不应套到自建引擎研究 |

技能是规则与工具入口，不能等同于已训练模型或已经执行的建造。流程文档的更新也不表示用户个人技能已自动安装或替换。

设计前维护同源的三份职责数据，可合在一个 JSON 中，但不能混淆：

| 数据 | 主要职责 |
|---|---|
| `design_brief` | 路线、关键词、硬约束、假设、证据、单位/坐标、seed |
| `spatial_spec` | 体块、各层标高和楼板、房间、核心、挑空、连接、露台、场地、保护区 |
| `facade_spec` | 立面区域、系统、开窗组、材料、承托花槽、采用的变化结果 |

给体块、房间、窗区和构件稳定 ID。已有坐标必须继承或显式转换，不静默翻转轴向。先处理楼板、挑空、核心、通廊和入口，再设计外观细节；相邻房间不证明存在门，核心位置不证明楼梯可达，透视图中能看到空间不证明其净高足够。

## 3. 将“随机”拆成独立且有条件的变化

随机变化从大到小依次作用：**布局与体量 → 按用途划分的立面系统 → 构件与花槽 → 材质点缀 → 旧化**。各层有自己的允许范围和冻结条件。给立面换颜色不能算布局随机；换盆栽不能算体量变化。

| 通道 | 可以变化 | 应保持或先确认的内容 |
|---|---|---|
| 地形/场址 | 已授权的局部地形、候选场址取舍 | 山脊、水系、保护树与填挖预算 |
| 布局/体量 | 位置、方向、长宽比、L/T/院落、错层 | 主用途、可到达性、已认可体块和核心 |
| 立面系统 | 实墙、竖窗、横窗、格栅、凹廊的有组织分区 | 内部用途、采光、结构和保护窗区 |
| 窗组/窗沿 | 整组起止、长短、数量、附属构件疏密 | 人工确认的可开窗区、承托和通路 |
| 玻璃点缀 | 同类材料的小组色差 | 主色比例、透明性、厚度、BlockState |
| 旧化 | 按年代/维护/暴露分配表面变化 | 门窗、体量、连桥及结构完整性 |
| 内饰/植物 | 合法位置中的活动物件、植物组、软装变化 | 主家具、门、通路、使用面、隐私和照明覆盖 |

每个通道保存算法版本、seed、稳定 ID、候选集合及采用结果。下游优先消费结果表，不能导入时重新抽样。认可后冻结的区域应通过结果差异检查证明没有连带变化。

两个立面计划器均以 seed 和稳定键的 JSON 序列经 SHA256 生成确定性数值，不依赖顺序消耗随机数。因此，同 seed 重跑、重排输入和新增独立区域/窗组的目标测试均可保持已有结果。它们的序列化细节不同，属于两个算法命名空间，不保证同 seed 同键产生同一数值。

隔离有明确边界：同一区域增删面板可能改变配额截断，重新选择部分原有面板；花槽 `group_id` 要全局命名，跨区域复用同 ID 会相关选择。不能宣传“增加任何元素都不会影响已有输出”。

## 4. 开窗、材料与旧化的具体学习

当用户认为窗沿或窗带“过齐”，首先调整整组窗的起止、长短、窗数和留白，再处理花槽与颜色。只换玻璃色，或固定奇偶层重复同样位置，不能解决窗组组织问题。

`plan_openings.py` 接收人工给出的 `allowed_u_m`、`base_u_m`、`floor_height_m`、窗型和数量，输出局部坐标中的窗组与窗沿。输出应替换旧洞口几何，不能叠加到旧逐开间洞口上。它不会识别照片中的安全区，也不解核心、门洞、逃生、采光或三维碰撞。

`fixed` 当前只有部分锁定语义：普通跨度下保留组范围/数量，但单窗宽、窗台/窗头和窗沿仍随 seed 变化；窄组还有被最小 1.1m 规则扩大范围的已知缺陷。不能把该字段当作已批准几何的完整冻结机制。

`plan_variation.py` 对已设计面板分配玻璃点缀和旧化，并选择声明合法的花槽候选。玻璃点缀按每区域合格面板数乘比例后向下取整；分母是合格面板数量，不是整栋方块数量或玻璃面积。花槽 `planter_density` 则是**组级选取概率**，不是最终数量配额；同组可全部选中或全部不选。

新建现代建筑可以用少量玻璃点缀、较高维护值作为艺术起点，但这些参数不是法规、实测统计或物理模型。主材料应占优势；玻璃块与玻璃片不能因颜色变化随意互换。夜间灯光独立管理，黑玻璃不等于空洞。

旧化先区分楼龄、上次翻修、维护和暴露：已知翻修时，`effective_age=min(age_years, years_since_renovation)`；再按当前算法计算：

`min(effective_age/80,1) × (0.20+0.80×(1-maintenance)) × (0.60+0.40×exposure)`。

合法的 `weather_override` 可显式替代公式。输出只是每面板的强度提示；真正的窗台下流挂、接缝、雨水管和材料污损需要额外表面遮罩。维护良好的老建筑可以整洁，不以随机缺砖或破玻璃制造结构损坏。

随包示例实跑得到：72 面板中12保护实墙、60合格玻璃面板；点缀比例0.06得到3个点缀面板。10个花槽候选中9个声明合格，当前seed选中6个。楼龄3、维护0.9、暴露0.6得到有效旧化强度0.00882。这些是此输入的结果，不是推荐的固定城市配额。

## 5. 功能内饰先于“填满房间”

每间房明确容量、活动链、3–5个主要功能组、支撑储物、使用面及进出方式。面积分别登记为活动家具、主通路、操作/门扇净空、有意留白和未设计区；未设计空地不能自动叫作通道。

目录中的12类用途为：图书馆、市民公共空间、办公室、会议、博物馆、画廊、餐厅、市场、酒店、住宅、学校、诊所。它们是功能研究卡；诊所卡只是空间意图，不是医疗设计规范。当前固定样板仅覆盖和菓子店、旅馆客房、现代阅览室、乡村厨房饭厅，其他用途没有因此获得通用布局求解器。

图书馆需要分类书架、检索/展示、阅读、借还及其关系，咖啡是可选次功能；餐厅需要迎宾、点单、出餐、回收与服务边界，不只是桌椅。博物馆/画廊需要观看距离、展陈序列和留白；办公室不能每层都变成休息厅；酒店要区分房间、走廊、服务和隐私。

内饰范围采用 L0–L3 分级：L0不添加未要求的隐藏家具；L1完成可见窗口片段的用途识别；L2完成入口及公共区；L3按实际边界设计可进入房间。完整照明不等于完整家具，窗口陈设不等于可进入空间。

完成房间时同时设计墙、地、顶、开口和家具软装。门必须联合检查门框平面、门扇平面、门槛、门柱、门楣、上下半、铰链和开启净空；只检查门前后有空格，会漏掉门扇退入框后或洞口过高的问题。

坐标交接要明确：合同 `floor_y` 为地板上首个站立空气格，地板在 `floor_y-1`；构件工具的局部 `y=0` 是地板块，`y=1` 才是站立格。不能直接混用。

## 6. 家具、植物与软装一起研究

家具细节按主体、支撑、软垫/背靠、边框/扶手、台面/门板、使用侧分层。先把一件家具和一个活动组做好，再扩展整间房。数量、倒置楼梯的名称或平涂盒体预览，都不能证明精细度合格。

原技能中确有四个 `FurnitureDetailKit` 固定配方：`framed_daybed`、`bed_wall`、`kitchen_band`、`mixed_cabinet`。它们调用 `InteriorKit` 的 emit 回调生成方块和组件/实体元数据；不包含自动旋转、缩放、全屋摆放、碰撞求解或 NBT 序列化。真床与装饰床分别标记；桌椅不承诺原版坐下动作，床、桶、炉的功能仍需实机测试。

独立试跑五次配方调用确认输出边界、床头尾配对、应有实体元数据、声明使用点、重复确定性和原点平移。两种宽度的daybed状态通过；另三配方部分原生方块不在恢复基线的验证词表中。合法Minecraft方块和“当前适配器已经支持”是两回事。

植物应与家具和软装一起组织，安排主景、次景、呼应与留白，检查容器、枝干、叶冠、承托和维护面。候选筛选必须覆盖整株体积与使用面，放不下就减量或跳过；不把全屋同盆等距排列当作自然感。

已有 `potted_bamboo` 单格固定原语；按 `plant_seed / room_id / group_id` 隔离的成组随机规则与平面试验也已记录。但平面试验为 `schematic_only`，没有成为通用植物NBT消费者。悬吊、垂枝、叶片保持、生长更新、完整冠幅和游戏碰撞仍须专门验证。

18个研究模块覆盖4类沙发活动组、厨房/茶水、3类植物与入口组、工位、会议、书架阅读、床组、窗口片段，以及点单/亭/卡座/矮隔断/窗边吧台。它们均保持 `research_only`；有关联小样不等于这些卡已经逐项生成并验收。

## 7. 灯光与园林的约束

现代空间默认考虑两层分隔：上层地板与下层天花/灯具。发光块替换天花层，不藏在不透明层后，也不无理由悬在完整天花之下。中世纪方案可用单层楼板与有支撑吊灯，仍要检查下垂净空。已有标高、楼梯、挑空和桥下净空锁定，不能为了灯具静默抬高楼层。

已知为1–9层时，规则要求覆盖所有已设计功能房、通廊和楼梯；总层数未知就保持未知，不能硬套。冷暖材料是视觉意图，不能推导原版彩色光传播。实际亮度、光照覆盖、刷怪与交互需要客户端验证。

六类园林研究卡为市民树荫前场、安静阅读庭院、石铺回廊前庭、展馆留白花园、自然式观水花园、餐饮街角/口袋绿地。建议尺寸只是起点，不是实测标准或自动生成器参数承诺。

先处理授权场地、主次入口、公共穿行和后勤，再放偏离主路线的座椅、乔灌草、视线与维护路径。检查完整路宽而非中心线；踏步石不能成为唯一通道。水景需要用途、边界、池底/边缘、水源和与人流的关系。新市民前庭默认无水池，不应反向推翻某个已认可案例的水庭。

## 8. 地形先行，避免建筑放好后整片削平

保存输入地形与哈希，区分地面、树冠、水、桥、建筑和空洞。程序生成地形不能称为原生 Minecraft 种子地形。先冻结山脊、峰、陡坡、水系、岸线与保留树，再按坡度、相对高差、到达和用途选址。

候选地块不合适时，依次尝试移动、转向、改变长宽比、L/T/院落与错层，再考虑局部填挖。记录每栋原高程范围、首层、足迹、入口、填挖范围和取舍；平台只覆盖建筑和必要活动。超过预算则重选场址或体量，保护山体需要建设前后差值。

先公共路网、节点和跨水连接，再分地块。道路需全横断面连续、落脚合理、台阶方向正确、桥不截断河道；A*能到一个点，不代表整条路可用。可步行和需要跳跃也应区分。

前后院、私公、门和服务面通过墙、篱、绿篱、铺地与高差表达，不随机断墙冒充院门，不把整个谷地铺平。河岸用不连续砂砾、石、根部和坡面过渡，并处理重力与水封闭。地形有主脊、侧坡、鞍部、冲沟；树林有连续林冠、林缘和下层，不是规则山包与等距球形树。

这些是地形设计和验收规则，当前技能没有任意地形自动选址、规划与NBT建造的通用求解器。每项输出应标明是研究、建议、可生成配方、本案应用还是实机通过。

## 9. 五类图与 HAF 交接

从同一空间与立面数据生成五类图：主视意向、关键剖面、每种不同层型的布局/动线、分层爆炸、四向立面。它不是固定五张图：剖面数随问题增加，不同层型不能压成一张首层图。

精确平面、剖面、爆炸和立面由同源几何绘制；图像生成可表达主视意向或氛围，但没有与几何对齐就标“意向”。爆炸只为展示拉开Z方向，真实XY及层高不变。机位、剖切、图像/几何哈希、长短提示词与尚未对齐的差异一并保存。

HAF交接使用整数块、Y-up、半开 `bounds_xyz`。应交付稳定ID、楼板/挑空/核心/通廊、用途、首层与上层标高、入口、可编辑区/锁定组件、全体积keepout、拟放模块及使用面、照明覆盖和水景理由。缺入口、未知证据或未消费字段保持pending。

现有 `compile_handoff` 是**计划消费者**：校验字段、边界、锁定ID、模块盒体与通路禁放区，输出建议天花及房间灯光任务；不生成整栋NBT，不推断家具，不修改旧run。仅存入 `input_snapshot` 的扩展字段不能算已经执行。

## 10. 能力与验证矩阵

| 范围 | 本次确认 | 未完成边界 |
|---|---|---|
| 同源空间/五类图/稳定ID | 明确规则及数据合同 | 不等于任意数据已被引擎消费 |

原样完整四房生成在当前恢复基线上因缺 `rural_states` 退出，另需 `nbtlib` 及专用渲染模块/资产；相关state词表亦不完整。本次没有为制造通过而注入替代模块，不把emit小测描述成NBT/渲染/游戏端到端通过。本实验分发不包含这一不完整依赖链。

验收状态分别记录 `data_checked`、`geometry_checked`、`visually_reviewed`、`engine_consumed`、`game_checked`，必要时另记 `aesthetic_status: needs_revision`。源码可执行、NBT能读回、离线图可见、实机可用与用户认可，是不同证据，不能自动晋级。
