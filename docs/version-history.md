# Haibara’s Architect 历代演进：从案例生成到共同验收

HAF 是一套由建筑研究、显式参数、案例适配器和文件检查组成的 Python 工程。本页沿真实代码与归档输出介绍 0.1–0.5 的变化，便于先理解问题，再阅读实现。这里的“学习”是规则、程序和案例的积累，没有模型权重训练记录。

具体入口、NBT 和阅读练习见 [案例学习指南](case-studies.md)；机器可读索引见 [case-index.json](case-index.json)。

## 先分清三种版本

| 名称 | 记录什么 | 例子 |
|---|---|---|
| HAF 引擎发布 | 共享代码、CLI、目录与验收接口 | HAF 0.4.0 |
| 建筑方案 / run | 某栋建筑的设计和一次保留的生成结果 | 市民中心 V0.3.3 / `v03_r16_ceiling_landscape` |
| Skill 规则 | 研究、设计、编排和交付约定 | Architect 工作流规则 0.4.1 |

它们不需要同步递增。Civic R16 的原始 `manifest.json` 写着 **HAF 0.3.0**，后来被纳入 HAF 0.4 发布；这个历史字段保留。多栋后来纳入 0.3 的案例，原始生成报告仍写着 **HAF 0.2.0**。整合发布不会追溯修改过去的版本。

**HAF 0.5 是研究与成果总库版本。** 该总库登记的可执行主线快照仍是 0.4.0，外部分支保留各自引擎与建筑版本。

## 各代解决的问题

| 发布 | 目标与代表类型 | 针对的细节 | 留下的边界 |
|---|---|---|---|
| **HAFusion 0.1** | 广州塔：开敞塔架、核心筒、多层场地 | 单写入者与阶段缓存；几何和材质分离；外框、环梁、核心、塔冠分别取舍；V6 r02 修复核心灯位沿用旧绝对坐标的问题 | 是广州塔专用融合路径；缓存可重放不等于外形更准确 |
| **HAF 0.2.0** | 发布时登记深圳报业、周大福两类现代办公塔 | 水平/竖向幕墙层次；稳定房间灯光；薄构件、窗后层、局部伪内饰与障碍灯样板；增加 `--version` 和 `--catalog` | 本次主要整理已有能力，没有新增通用生成算法；局部 Detail V2 不等于整栋 V2 |
| **HAF 0.3.0** | 合并十个案例入口：现代塔楼、钟塔、宫殿、纪念堂、住宅和车站；另记广州塔、琶洲两例历史对照 | 最终 NBT 的承托/净空/材料采样；旧失败到修复版本的对照；四个等尺度斜视和真正俯视；保存分项反馈 | 多数建筑先在 0.2 分支完成，再于 0.3 整合；共享采样只覆盖声明位置 |
| **HAF 0.4.0** | 加入原创市民服务中心，形成十一条生成入口 | 用途、公共区与后台；成组家具；两格层间构造、嵌灯、净高例外；整片园林与全宽路径；可执行设计交接检查 | `--handoff` 输出计划，不输出建筑 NBT；Civic 仍是冻结案例适配器 |
| **HAF 0.5 研究整合版** | 按七类风格整理二十三条案例，含现代高层、公共建筑、住区、城中村、乡村聚落；另记十五个专题/产品支线 | 独立分支版本和失败账本；布局、分布与随机性分开；二十种子 × 四策略的二维比较；稳定对象 ID 与随机通道实验 | 二十三条不是二十三个主线适配器，也不是二十三个独立泛化样本；二维实验未统一接入体素建造 |

这些是每次发布的范围，不是建筑风格自动识别能力。铁路、工业设施与城市规划的后来成果，应在真正接入共享代码和验收后再计入核心；研究报告或单个专用脚本本身不改变上表。

## 0.1：先把一次生成变成可以追溯的过程

广州塔把“建筑是否像”和“程序是否稳定”分成两件事。外框、内部环、核心、功能玻璃层、塔冠和场地拥有各自的输入及取舍记录；材质替换不能越过被冻结的几何范围。曾有灰色混凝土替换触及保护广场而失败，这类结果保留下来作为边界证据。

阅读入口是 `hafusion/pipeline.py`、`hafusion/cache.py`、`hafusion/evidence.py`，以及 `history/canton/` 下的记录。**当前案例清单尚未附齐 V6 r02 最终 NBT 与完整原输入**，因此不把这条历史入口写成开箱即可复跑的示例。它也不是任意 SKP 自动融合器。

## 0.2：现代塔楼把构件层次和随机性具体化

深圳案例主要检查横带、玻璃和窗后进深；周大福转向竖梃、弧面转角和安全灯位。稳定种子必须绑定房间身份，新增一个房间不能使其他房间全部重新抽样。固定冠灯和普通窗灯是不同任务。

发布时增加的控制目录，负责告诉使用者“哪项参数确实有人读取”。例如存在 `crown_accents` 字段，不意味着整栋已有正确冠灯；研究中的障碍灯样板也不能算作真实红色投射光或闪烁。

对应文件：

- `cases/shenzhen_press/src/build_case.py` 与 `research/parameters.json`
- `cases/guangzhou_ctf/src/build_case.py` 与 `research/parameters.json`
- `hafusion/lighting.py`、`hafusion/facade.py`
- `docs/HAF_0.2.md`、`releases/0.2/validation.json`

## 0.3：跨类型后，共同检查开始有意义

十条入口分别是：

`shenzhen_press`、`guangzhou_ctf`、`namsan_tower`、`elizabeth_tower`、`buckingham_palace`、`nanshan_cloud`、`guangzhou_customs`、`guangzhou_memorial`、`zhujiang_dijing`、`guangzhou_south`。

南山塔带来地形和台地；古典案例带来厚墙、窗洞和线脚；纪念堂暴露柱脚与屋面接缝；南站暴露“玻璃开了门，后来加的竖梃又堵住门”的最终拼合问题。这些差异说明：不能只检查单个构件函数，必须重新读取最后交付的 NBT。

共享实现位于 `hafusion/review.py` 和 `hafusion/views.py`。纪念堂和南站已声明采样契约，其他案例保留原有检查；没有契约的案例仍应显示待检查。视图元数据正确，也不能替代实际看图。

## 0.4：从外壳走向可解释的空间关系

Civic 的建筑方案经历 R06、R10、R13 至 R16：先补用途和成组家具，再补照明，最后处理下层吊顶、嵌灯与整片园林。R14/R15 发生路径侵入，因而最终检查从中心线扩展到路径的完整宽度和净高。

共享的 `hafusion/design_handoff.py` 消费用途、稳定 ID、编辑边界、锁定构件、楼层标高、模块包围盒与禁放通道。输出明确标记 `generated_geometry=false`。十二类用途、六类园林和十八张研究卡是设计目录，不能据数量推断存在相同数量的自动生成器。

Civic 当前入口从 R13 冻结结果重做 R16；生成需要 R13，内饰对比还需要 R06，照明对比需要对应离线光场。把所有旧 run 删除，只留下最终 NBT，会破坏这条学习和复核链。

## 0.5：把分散成果登记清楚，再研究场景分布

总库补入西塔、东方明珠、环球金融中心、大阪与广岛案例，以及中信广场、千禧住区、榕荫里、田埂里等独立分支。它也纠正旧结论：琶洲后来已有 V3b 幕墙分层与连接修订，但整栋视觉反馈没有因此自动关闭。

布局实验区分规则网格、独立散点、最小间距、沿路组团约束。冲突统计只针对二维足迹和简化禁建区；没有包含真实坡度、门口通达、玩家碰撞或水更新。下一个有价值的验证是让同一组房型在不同场地产生可解释的不同布局。

本仓库索引保留这些分支的案例版本和缺口。未实际附带的源码/NBT 会明确标记，不使用作者的私有存储链接作为公开下载入口。

## 更早的基础工程

| 基础模块 | 作用 | 与 HAF 的关系 |
|---|---|---|
| BuildKit 0.3 | 柱廊、方块状态、NBT 与局部差分 | `ha03/vendor/buildkit_v03/` 下的工程依赖 |
| Architect 0.1 | 参数 → 构件 → 方块 → NBT | 便利店、塔段和廊柱等早期例子 |
| Architect 0.2 / BuildingSpec 0.2 | 证据绑定、保护区与修订守卫 | 局部修改主要通过全量重建和差分检查实现 |
| Architect 0.3 | 模型单位、轴系、层级、材质与来源研究 | 模型 attach 增加候选证据，不自动改变执行几何 |
| HA R0.3 / Detail Lab | 仲裁、缓存、已知锚点和细部实验 | 研究原型与局部样板，各自保留验证范围 |

不要把 BuildKit 0.3、Architect 0.3、HA R0.3 和 HAF 0.3 当作同一版本。

## 怎样理解历史验证数字

0.2 留有二十三项核心测试，0.3 留有四十八项单元测试与二十五项发布检查，0.4 留有六十二项单元测试与三十二项发布检查。这些数字属于当时的代码和环境，不是还原准确率。0.4 的五十项 Civic 检查已作为汇总包含在发布检查中，不能相加声称八十二项互相独立的验收。

文件、几何、视图元数据、人工视觉、用户接受和游戏可用性分别记录。本文各历史案例的实际 Minecraft 导入、碰撞和真实光照均保留待验证状态。


## 0.6：把约束、随机与模型提案放入可运行的工作流

新增 `hafusion/workflow06.py`、`variation06.py` 和 `tools/haf.py`。阅读空间示例可以创建计划、独立通道随机结果和父子修订记录；模型只提出JSON，宿主绑定目录和父版本。冻结、边界、通道和文件一致性由代码检查。

这是运行层0.6，保留几何内核0.4和交接schema0.4。阅读空间只形成计划，尚未转成新建筑NBT。另用既有钟塔适配器实际生成新的 `cases/elizabeth_tower/runs/HAF06_smoke_01/`：112,474非空气方块、152组窗，最终NBT回读完全一致。这次实跑验证了整合后的建造入口，不能当作新建筑算法或游戏内通过。
