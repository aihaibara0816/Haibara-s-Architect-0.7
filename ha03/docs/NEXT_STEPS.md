# 下一阶段开发记录

当前最大缺口是**从真实研究证据得到可执行几何约束，并在游戏内证明可用**。单纯增加建筑知识或形容词，无法补上门洞坐标、层高、体量关系和截面控制点。

## 0.1.1：完成游戏内验收

取得测试实例的真实Minecraft / NeoForge / Create版本与方块注册表。在空白测试世界分别导入便利店和塔楼，记录放置方式、坐标、截图、门洞/屋顶/玻璃/灯块表现，以及Create是否能实际读取当前NBT。输出game_test.json，标明tested版本、构建哈希、通过项与失败项。当前不需要修改正式服务器。

若Create不接受该结构格式，先分析实际错误，再做格式适配；不要只改后缀。超过适用导入或世界高度时保留统一比例，开发分块placement_manifest，不能静默缩小。

## 0.2：研究 → 几何约束 → 施工决策

复用`gafacraft-building-reference`搜证和选图能力，但在自然语言报告与BuildingSpec之间增加一层可审阅的几何提取结果。

| 提取内容 | 可执行表示 | 不确定时的行为 |
|---|---|---|
| 主体与附属 | 体量ID、父子关系、相对位置、边界 | 分开候选，不混入背景楼群 |
| 尺度 | 原尺寸/范围、比例、锚点、证据ID | 真实值null；试建值放design_choice |
| 立面节奏 | 开间数、重复轴、层高、门窗区域 | 指明哪些是看到的、哪些是工程补全 |
| 轮廓 | 多边形、屋面高程、退台线 | 低置信区域标待审核 |
| 塔楼截面 | 高度锚点、中心、宽深、旋转候选 | 先用可解释截面，不让引擎自由猜曲面 |
| 施工约束 | 可达入口、净空、楼板、目标材质 | 转成自动检查和待游戏验收项 |

模型输出只允许受Schema约束的数据。后端拒绝未知材质、无证据精确值、比例冲突及越界几何；错误结构化返回模型做有限次数修复。工程层保持确定性。原始用户输入必须在扩写之前保存，避免扩写覆盖需求。

首轮用已有廊柱、便利店和变截面塔楼三个类型，各补一组有来源的多视角案例；记录“输入 → 提取约束 → Spec → 输出 → 修改意见”。人工检查轮廓、比例、节奏、开口和通行，先形成小而可靠的评测集。照片授权不明时不进入训练集。

## 0.3：构件库与局部编辑

增加斜屋面、楼梯、半砖、栏杆和定向方块，必须让渲染几何与实际state一起升级。将盒体组合沉淀为有约束的建筑构件模板，例如入口、窗墙、柱廊、楼板核心筒；避免新案例都写专用生成器。

支持“只把雨棚加宽”等编辑指令 → component_id及参数补丁 → 新revision → 前后NBT区域差分。现有雨棚实验已证明输出变化可限制在目标区域，但尚未做到内部增量计算。

## 网站对接与训练时机

游戏验收与约束提取稳定后再接网站。技术接口见WEB_INTEGRATION。先复用现有多模态模型与Skills；只有积累有授权、成对且经评价的数据后，才根据错误分布决定是否训练小模型，以及训练提取器、排序器还是其他模块。当前没有理由先开展无目标的大规模关键词收集。
