# Haibara’s Architect｜开源研究与本地实验 R0.3

2026-10-21 · 本轮状态：研究与隔离实验完成；正式架构接入待用户确认。

**建议保留 Architect 0.3、BuildingSpec 0.2 和已有两份个人 Skill，以小适配器吸收上游机制。优先补证据裁决、可复现环境、量化取舍与独立评测，再考虑引擎缓存和视觉几何模型。** 不建议把任一上游项目整套换进来。

本轮读取了提供的 v0.2 研究包，核对 7 个 GitHub 仓库的实际分支、提交和 60 个源码/说明文件，执行已有回归与新实验。没有修改已安装 Skill、正式工程、网站或 Minecraft 世界，没有生成广州塔 V6。新代码均在独立研究目录。

## 2. 几条路线怎样组合

| 路线 | 最适合的任务 | 优点 | 关键限制 | 本轮建议 |
|---|---|---|---|---|
| 文字/图纸/照片研究 → 参数化构件 | 楼层、入口、幕墙节奏、裙楼层级、缺少模型的建筑 | 参数可解释，便于局部修改，纯图片路径可以保留 | 语义与尺寸仍需研究判断；看见遮挡不等于知道深度 | 继续作为主线；学习 PlanCraft 的结构化尺寸和净空策略 |
| 经审核模型 → 构件几何 → 方块化 | 扭转主柱、复杂塔身、斜塔冠、明确网格细节 | 保留空间走势与复杂形态 | 模型年代、比例、材质、重复实例可能错误；整体体素化可能堵住镂空 | 保留现有 model_io，按构件选择，研究 ObjToSchematic/Arnis 的采样与材质机制 |
| 多视图预测 → 相机/深度/候选表面 | 没有模型但有重叠视角的建筑局部 | 可辅助理解空间关系与照片对应 | 需要可用权重和算力；未自动得到构件语义、可靠尺寸或许可 | VGGT 作为后续可选 provider，先做有锚点的局部对照 |
| GIS/街景/高程 → 建筑群与场地 | 校园、街道、地块、大范围布局 | 坐标和场地拓扑有基础，易扩展到区域 | 普通墙面/地块假设不能直接解释广州塔格构、复杂裙楼 | Arnis 做独立场地适配器候选，不并入单体核心 |
| LLM 直接输出方块 JSON | 小体量概念草模、交互演示 | 接口直观，反馈快 | 缺结构契约；大结构编辑可能只带局部上下文；难保留所有权与尺度 | 仅借鉴交互，不作为主构建路径 |

对广州塔，合适的融合仍是：塔身走势采用审核过的模型；功能楼层与玻璃分段采用照片/图示；塔冠采用有依据的斜面；场地采用同年代建成资料和显式层级。**每个构件可以采用不同来源，同一构件的形状、材料、尺度也可以采用不同来源。** 冲突应形成取舍记录，不能把两套形状取算术平均。

Arnis 的多视图颜色中位数是在同一个已配准墙面采样格上融合颜色，不能理解为整栋建筑的图片/模型平均。它也不能保证消除所有遮挡：固定遮挡、缺少相机位姿和跨年代差异仍会出问题。

## 3. 源码核查后必须修正的认识

1. **Arnis 当前墙面拟合不只是随机 RANSAC。** `src/mapillary/plane.rs` 已采用围绕墙方向的确定性角度搜索、投影滑窗和两轮最小二乘细化。点不足或方向偏离会退回原轮廓，并保留失败统计。源码注释指向的 `tools/facade_lab/plane.py` 不在本次公开提交树中；不能承诺拿该 Python 文件直接跑。
2. **不能把“保留净空”设成所有建筑的唯一量化目标。** PlanCraft 的分段坐标变形会改变总宽度；薄墙默认材质还涉及较新游戏方块。塔身外轮廓、房间净空、细框架和相连场地应分别选择策略，并约束接口。
3. **现有 `geometry_sha256` 不是纯占用形状哈希。** BuildKit `Scene.fingerprint()` 包含坐标与方块状态。将来增加 `occupancy_sha256`、`ownership_sha256` 等旁路指标，保留旧字段定义；否则“只改材质”的实验会被误读。
4. **互通网格不等于互通可编辑构件。** PlanCraft 的最终 Grid 不保存我们需要的逐单元 component_id。此次桥接只赋予一个测试构件 ID；正式接入必须在编译前/编译时保存构件归属，不能给最终网格随意补标签就称组件化完成。
5. **现有 BuildingSpec 已有模型来源、参数证据绑定和组合约束。** 不需要再发明另一套 BuildingSpec。缺口主要是候选证据到现有字段的受控适配，以及更复杂构件的执行适配器。
6. **文件验证与游戏验证应继续分开。** PlanCraft 的 readback 比较允许部分状态差异；我们的水、透明构件、半砖、楼梯需要目标版本注册表和实际碰撞/流体检查，不能照搬所有忽略规则。

## 4. 最小成本吸收顺序

**第一批：可审计、可复现。** 整理实际通过的依赖配置；增加外置的属性证据表和候选取舍报告；固定输入/相机/范围；给现有生成结果补纯占用与所有权度量。优先增加适配器和旁路 JSON，保持 BuildingSpec 0.2、生成器和 NBT 主链。

**第二批：针对性构件改进。** 让室内/通道借鉴净空量化，薄壳/杆件先做独立样板，配合外形偏差与镂空测试。再将几何、材质、照明分离到能独立测量的执行边界。只有正确性对照通过后才把缓存接入主引擎。

**第三批：新增资料提供者。** 选择一块立面做 VGGT 与人工锚点对照；选择一个校园区域做 GIS/场地适配；交互 Studio 和大规模调度留待这些接口稳定后。

建议的下一代职责是“文字与来源研究、图片证据、模型证据、构件取舍、构建与验证”。它们目前是设计职责，不是已安装的五个新 Skill。先在现有两个个人 Skill 中补充经过验证的规则，是否拆成独立 Skill 再按重复使用情况判断。
