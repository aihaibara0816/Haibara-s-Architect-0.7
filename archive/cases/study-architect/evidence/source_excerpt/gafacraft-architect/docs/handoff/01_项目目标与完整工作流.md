# GAFAcraft Architect｜项目目标与完整工作流

> 项目阶段：2026-10-20 方案基线（待 Work 对源码和运行环境审计后更新）  
> 项目定位：面向 GAFAcraft 玩家、未来可部署到 `gafacraft.cn` 的 Minecraft AI 建筑复原系统。  
> 交付策略：先完成可运行的本地端到端原型，再做网站与公共服务部署；不把研究报告等同于已经生成建筑。

## 1. 产品目标

最终用户只需输入建筑名称、简短一句话、上传一张或多张参考图片，就能得到尽可能有依据的 Minecraft 建筑蓝图。系统应能主动补全资料，区分事实和假设，输出可追溯的建筑结构参数；由确定性的参数化生成器制作方块，而不是让生成器自行猜测建筑。

最终交付：真实方块数据所生成的固定视图预览、可导入的 Java 结构 NBT（优先验证 Create Schematic 兼容性）、建筑规格、资料证据、错误和偏差记录。用户可提出“只改塔顶”“收窄中段”“增加灯光”等修改，系统尽可能保留未被要求修改的构件。

**MVP 不是自训大模型**：先用现有语言/视觉模型 + 已有 Skill + 参数化 Python 工具，逐步积累可验证的案例。未来是否需要模型微调，以实际性能缺口和数据质量为准。

## 2. 确定的交互原则

- **轻输入**：允许只有建筑名称、一句话或几张图；不要求用户自己写长 Prompt 或建筑参数表。
- **Skill 在前、引擎在后**：Skill 主动检索、分析多视角参考、推理体量和尺度、整理材料、生成结构化规格；生成引擎只读取明确参数，不做隐式设计推测。
- **固定五视图**：前立面、后立面、左立面、右立面、斜上 45° 轴测图。俯视、日夜切换与自由旋转都不是首阶段阻塞项；日夜光照后续可增加。
- **真实方块驱动的预览**：预览应由和 NBT 相同的方块数据产生，不得用 AI 意境图冒充已生成的 Minecraft 建筑截图。
- **可解释与可回滚**：建筑关键尺寸、推断和风格选择有证据来源，局部调整保留组件 ID、旧版本和差分。
- **比例优先遵守用户指定**：明确 1:1 时遵守 1 格≈1 米；如超出游戏高度、尺寸或资源预算，提示阻塞与替代方案，未经许可不自动缩放。
- **内部空间分层**：可以仅复原外观、保留通行空间、构造关键内部或全面室内，默认不臆造不可见的现实内装。
- **先本地、后公用网站**：先打通生成—校验—导出，再实现上传、排队、账户、存储、速率限制和部署。

## 3. 完整工作流（正式目标）

### 阶段 A｜输入与需求解析

输入：建筑名称、文字任务、参考图（0～多张）、比例、游戏环境要求、输出用途。保存原始需求、上传图、来源和任务 ID。自动识别是否为真实建筑、幻想建筑或无明确建筑身份的案例；身份模糊时询问关键问题。

### 阶段 B｜Skill 建筑研究与证据包

优先复用 `$gafacraft-building-reference` 与 `real-to-minecraft` 的现有规则：确定建筑身份；查询可靠尺寸、楼层、历史状态与建筑设计信息；整理正/背/左/右/屋顶或侧上视角；分析主次体量、轮廓、收分/退台、立面、材料和灯光。生成 `packet.json`（证据/资料包）和必要图片引用；每个数值必须记录 `source_id` 和 `status`（confirmed / observed / estimated / design_choice / unknown 等）。

重要：**`packet.json` 是事实与参考资料包，不等同于新提出的 `BuildingSpec`。** 不要覆盖已有 `references/packet-template.json` 与 `data-contract.md`，先检查其兼容性并保留证据来源。

### 阶段 C｜从证据到 BuildingSpec v0.1

把资料包转换为能够施工的 `building_spec.json`；使用 JSON Schema 检查字段类型、单位、必需项和约束。内容至少区分：

1. 项目身份、目标游戏版本和输出形式；
2. 原始米制尺寸、可用来源与采信状态；
3. Minecraft 比例、坐标原点、方向、高度边界；
4. 建筑构件列表及稳定 `component_id`；
5. 体量与关键截面、楼层、门窗、屋顶、楼板和公共流线；
6. 方块材质映射、灯光和可选内部结构；
7. 未核实事实、暂定施工参数和游戏内适配偏差；
8. 对应参考图、组件来源、审核与版本信息。

对无法查证却会影响建造的值：要么要求确认，要么在 **研究样板模式** 写入明确标记的 `study_parameters`，不能伪装为真实建筑尺寸；对严格复原模式的阻塞参数应停止正式生成。

### 阶段 D｜参数化几何与体素化

引擎按 BuildingSpec 构造实体、幕墙、开口、屋顶和可通行空间；统一单位换算，再离散化到 Minecraft 方块坐标。可先支持盒体、拉伸多边形、层叠体量、楼板、开口、平/坡屋顶，再增加塔楼随高度变截面、圆角、退台、斜撑和特殊曲面。禁止把输入中的自由文本当成几何引擎可执行代码。

输出真实的方块列表/方块状态/结构包围盒/材质统计；核心阶段应与具体 AI 模型解耦，同一份 BuildingSpec 能重复生成同一结果。

### 阶段 E｜校验和五视图

以同一份方块数据生成：前/后/左/右/斜上 45° 五视图；进行高度宽度、体量轮廓、材质、楼板净空、入口开洞、边界越界、NBT 索引/坐标等检查。与参考图比对时须注明相机、视角、遮挡和无法判断的内容。灯光预览或高画质渲染以后再做。

### 阶段 F｜自然语言修订（后续逐步完善）

用户给出“塔楼太胖，底部收窄”之类反馈；AI 先生成**针对指定构件的参数变更提案**，通过校验后重建受影响部分。保留构件 ID、不变约束、旧版产物、差分与回退能力。MVP 可先支持结构化修改参数，第二步再增加自然语言自动生成差分。

### 阶段 G｜导出与游戏实测

优先导出 Java Edition `structure NBT`；**确认 Create 6.0.10 / MC 1.21.1 的实际蓝图读取及放置/建造兼容性**，不能以扩展名 `.nbt` 就宣称 Create 能使用。导出实际 NBT、`placement_manifest.json`、参数文件、五视图、校验报告；大型建筑拆分时记录每段原点、拼接顺序与方块所有权。游戏导入与施工必须使用测试世界，用户明确同意前不得修改正式服务器存档。

## 4. 三层系统架构

```text
GAFAcraft Architect Web（未来网站）
  ├─ 上传图片 / 输入需求 / 任务进度
  ├─ 固定五视图 / 修订 / 下载
  └─ 用户任务记录 / 安全限制
                 ↓ API / 队列
Architect Intelligence（研究与理解层）
  ├─ 现有建筑研究 Skills
  ├─ 来源证据包 packet.json
  ├─ BuildingSpec 生成与 JSON Schema 校验
  └─ 用户反馈 → 组件参数修订
                 ↓ 严格的 BuildingSpec
Architect Engine（确定性执行层）
  ├─ 参数化建筑几何
  ├─ Minecraft 体素化、方块材质映射
  ├─ NBT 导出与静态校验
  └─ 同源五视图预览与项目版本
```

## 5. 当前与未来范围边界

**P0 技术闭环**：一个确定的 BuildingSpec → 实际方块 → `.nbt` → 五视图 PNG → 读取回验（从文件层验证）。

**P1 AI 预处理闭环**：一句话 + 图片 → Skill 资料包 → 经过校验的 BuildingSpec → P0 流程；优先有人工可检查的中间输出。

**P2 复杂几何与局部修订**：真实高层塔楼截面变化、幕墙、材料、灯光、内装、局部差分。

**P3 网站接入**：接入 `gafacraft.cn` 的架构评估、任务 API、排队、上传限制、预览下载、部署与容量管理。公网部署必须另行确认。

## 6. 验收的基本标准

- 本地真实跑通一栋小型建筑的可重现生成：规格、方块、NBT、五视图和校验报告全部是实际生成文件。
- 视图来自真实方块，不是单独的文生图；不同视角几何一致。
- Spec 中的事实、推断和未确认项可以追踪；资料缺口不得悄悄变成“事实”。
- 修改一个体量参数能得到可解释的新结果，并保留旧版本。
- NBT 可以被已有工具读取；在相应的测试 Minecraft/Create 世界验证前，游戏兼容性状态必须标 `pending`。
